# 前端設計簡報

用途：這份文件是 `docs/FRONTEND_SPEC.md` 的輸入。內容為使用者已確認的視覺方向與五個頁面的設計決定。
產出規格時，**視覺規範一節的數值必須原樣沿用**，不可自行調整色票、字級或間距。

---

## 1. 整體方向

- 風格：深色專業風，參考 OKX / Binance 等交易所後台。資訊密度高、數字醒目。
- 目標：面試 demo。畫面要能讓人一眼看出這是金融級系統，而不是一般 CRUD 網站。
- 桌機優先。手機可用即可，不需為手機重新設計版面。

## 2. 視覺規範

### 色票
| 用途 | 色碼 |
|---|---|
| 頁面底色 | `#0B0E11` |
| 卡片／區塊底色 | `#161A1E` |
| 次要按鈕、頭像底色 | `#1E2329` |
| 分隔線、外框 | `#23282F` |
| 主要文字 | `#EAECEF` |
| 次要文字、標籤 | `#848E9C` |
| 停用文字 | `#4A5057` |
| 主色（CTA、連結、當前分頁） | `#F0B90B`（黃） |
| 收入、成功 | `#0ECB81`（綠） |
| 支出、失敗 | `#F6465D`（紅） |

狀態區塊底色用主色的低透明度疊加（如 `#0ECB8119`、`#F6465D14`），外框用 `40` 透明度（如 `#F6465D40`）。

### 字體
- 介面文字：系統無襯線字體。
- **所有數字一律使用等寬字體**：餘額、金額、時間、hash、ID、error code。
- 字級：主要標題 15px、區塊標題 13–14px、內文 13px、標籤與輔助說明 11–12px。餘額主數字 32px，Explorer 金額 28px，指標卡數字 18–20px。
- 字重只用 400 與 500，不使用更粗的字重。

### 數字呈現規則
- 金額一律補滿至幣別的小數位數（USDT/BTC/ETH 為 8 位），例如 `250.00000000`。
- 千分位加逗號。
- 收入前綴 `+` 並用綠色，支出前綴 `−`（U+2212，非減號 hyphen）並用紅色。
- 時間精確到秒；Explorer 頁顯示到毫秒並標註時區。
- hash 一律縮寫顯示（前 6 後 4，如 `0x7f3a2b…c21e`），可複製完整值。

### 元件樣式
- 圓角：卡片 8px、輸入框與按鈕 6px、小徽章 4–5px。
- 外框：`0.5px solid #23282F`；輸入框聚焦時外框改為 `#F0B90B`。
- 主要按鈕：黃底 `#F0B90B`、深色文字 `#0B0E11`；次要按鈕：`#1E2329` 底、淺色文字。
- **每個畫面最多一顆黃色主要按鈕**，其餘用次要樣式。
- 收支方向除了顏色，一律搭配箭頭圖示（收入 `arrow-down-left`、支出 `arrow-up-right`），不可只靠顏色區分。
- 導覽列當前分頁：文字用主要文字色，下方 2px 黃色底線。

### 文案
- 介面文字用英文，句首大寫、其餘小寫（sentence case），不用全大寫或每字大寫。
- **所有錯誤訊息同時顯示人類可讀的說明與後端回傳的 error code**（code 用等寬字體、次要文字色）。這是刻意的設計，用來展示前端依賴穩定的 error code 而非比對文字。

## 3. 頁面清單與設計決定

共五個頁面，導覽列固定為：Overview / Transfer / History / Explorer，右側顯示目前使用者名稱與頭像縮寫。

### 3.1 Login / Register
- 單一畫面，兩個分頁切換（Sign in / Create account）。
- 登入失敗訊息固定為「Invalid username or password」，不透露帳號是否存在。
- 註冊：使用者名稱、Email、密碼三個欄位。帳號重複即時顯示錯誤與 `USER_ALREADY_EXISTS`。
- 密碼至少 8 碼，輸入時即時顯示強度條與規則是否符合。
- 頁面底部註明：帳號與錢包在單一 atomic transaction 中一起建立。
- 登入表單底部註明 session 有效期 24 小時。

### 3.2 Overview（錢包總覽）
- 上方：總餘額（32px 等寬，旁有眼睛圖示可隱藏金額）、24 小時變化、右側 Transfer 主按鈕與 Deposit 次按鈕。
- 中間：三張指標卡（總交易數、24 小時支出、24 小時收入）。
- Assets 區塊：各幣別列表，含幣別圖示、名稱、餘額、估值。
- Recent activity：最近數筆交易，含方向圖示、對象、hash 縮寫、金額、時間；右上角 View all 連到 History。

### 3.3 Transfer（轉帳）
- 欄位順序：幣別選擇 → 收款人 → 金額。
- 金額欄位上方右側顯示可用餘額，欄位內右側有 MAX 快捷與幣別標示。
- 欄位下方即時顯示限制：最多 8 位小數、單筆上限。
- 金額下方摘要區塊：轉帳後餘額、手續費。
- 主按鈕文字為「Review transfer」，**必須有確認步驟**，不可一鍵直接送出。
- 錯誤狀態需涵蓋：`INSUFFICIENT_BALANCE`、`INVALID_DECIMALS`、`SAME_ACCOUNT_TRANSFER`、超過單筆上限、收款人不存在。
- 成功後顯示交易 hash，可點擊前往 Explorer。

### 3.4 History（交易紀錄）
- 上方篩選列：All / Sent / Received 分頁、幣別下拉、日期區間、右側 Export。
- 表格欄位：方向圖示、對象與方向文字、交易 hash、金額與幣別、時間（時:分:秒 + 日期）。
- hash 可點擊前往 Explorer。
- 下方分頁：顯示「Showing 1–20 of 147」與頁碼控制。

### 3.5 Explorer（公開交易查詢）
- 右上角標示「Public」徽章。
- 搜尋框輸入交易 hash；下方一行說明：任何人持 hash 即可查詢，不需登入。
- 結果卡片：狀態標頭（圖示、完成時間、狀態徽章）→ From / To 兩側對照並以箭頭連接 → 置中的大金額 → 明細列表（hash、signature、幣別與小數位、交易 ID）。
- signature 欄位需標註為 demo 用途，非真實密碼學簽章。
- 頁尾說明：餘額與帳戶資訊不公開，僅交易本身公開。

## 4. 所有頁面都要處理的狀態

每個資料區塊都需定義：載入中（骨架屏，不要轉圈圈）、空狀態、錯誤狀態（含重試）、以及未登入時導向登入頁。

## 5. 後端目前不支援的功能

規格中必須有獨立一節列出這些，說明前端第一版怎麼處理，以及之後需要後端補什麼：

1. **列出使用者所有幣別錢包**：目前註冊只建立一顆預設錢包，也沒有列出全部錢包的 API。第一版只顯示單一錢包，Assets 區塊保留但只有一列。
2. **以使用者名稱查詢收款人**：轉帳 API 收的是 user_id，沒有依名稱查詢的端點。第一版收款人欄位直接輸入 user_id，介面上仍預留顯示名稱的位置。
3. **估值（USDT value）**：沒有匯率來源。第一版隱藏估值欄位。
4. **交易對象顯示名稱**：交易紀錄回傳 user_id，不含名稱。第一版顯示 `user #N`。
5. **Sent / Received、幣別、日期篩選**：後端尚未支援查詢參數。第一版篩選列僅顯示 All，其餘選項標為停用。
6. **24 小時統計**：沒有對應 API。第一版由前端從已取得的交易紀錄計算，或隱藏指標卡。
7. **Export**：由前端將當前頁資料轉成 CSV，不需後端支援。
8. **手續費**：系統無手續費概念，固定顯示 0 並標示為零手續費。

## 6. 技術選型

- Vite + React + TypeScript
- Tailwind CSS + shadcn/ui（需覆寫為上述深色色票）
- TanStack Query 處理資料存取與快取
- React Router
- API client 與型別由 `api/docs/openapi.yaml` 自動生成（orval 或 openapi-typescript），**禁止手寫**
- MSW 用於開發期 mock 與測試
- Vitest + Testing Library（單元）、Playwright（E2E 與截圖驗收）
- 位置：repo 根目錄的 `web/`；需在 `web/` 放置最小 `go.mod` 避免 Go 工具掃描

## 7. 前後端邊界（寫入規格與 CLAUDE.md）

- `web/` 只能透過 HTTP 呼叫後端，唯一契約是 `openapi.yaml`
- API client 與型別一律自動生成，禁止手寫
- 後端不得為前端加入 UI 專屬邏輯；需要新資料時新增通用 API
- 修改 API 時必須同步更新 Swagger 註解並重新生成前端型別
